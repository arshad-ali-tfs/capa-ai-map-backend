# Databricks Apps deployment preparation

For this service's standalone Docker image and local container startup, see [DOCKER.md](DOCKER.md). The Docker and Databricks Apps deployment paths are verified separately.

These instructions cover the standalone MAP backend and common frontend repositories. MATCH and AUTHOR have their own separate backend repositories and deployment guides.

1. Clone this service's repository with Git LFS. The source export, saved UMAP/FAISS bundle, reference files and pinned BGE checkpoint are now versioned together. Run git lfs pull and verify them with python -m capa_map.bootstrap after installing the package. Keep .env, installed dependencies, unrelated model caches, generated databases, run outputs and reviewer notes out of Git.
2. Prepare a code-only deployment directory or a deployment bundle that excludes data/**, .git/**, .venv/** and .local/** from app-source synchronization. Do not deploy the expanded Git LFS checkout directly as Databricks app source: individual app files cannot exceed 10 MB. app.yaml contains the start command. Python dependencies are declared in requirements.txt/pyproject.toml; the frontend uses package.json/package-lock.json and builds with npm run build.
3. Databricks mode requires an attached Unity Catalog table resource in `CAPA_SOURCE_TABLE` and a SQL warehouse resource with key `sql-warehouse` in `DATABRICKS_WAREHOUSE_ID`. In **Settings → Resources**, grant the app service principal **Can use** on the SQL warehouse and **Can select** on the table. `app.yaml` resolves the warehouse ID from that resource; setting the ID as a plain value does not grant access. The worker reads the table through the warehouse and writes a content-addressed CSV snapshot under `CAPA_DATA_DIR` for the existing pipeline; Databricks mode ignores flat-file source settings and fails at startup/run time if the table resource is missing. Local development continues to use the paired `CAPA_SOURCE_CSV` and `CAPA_SOURCE_SNAPSHOT` settings. Set `CAPA_DATA_DIR` to writable run storage. Point `MAP_ASSETS_DIR` and `HF_HOME` at the uploaded UMAP/FAISS/BGE artifacts in approved storage, such as UC Volumes; do not rely on Git LFS pointer files or bundle these large files into app source. Supply the model endpoint/key through Databricks secret configuration. The SQL connector is constrained to 4.9+ because earlier preinstalled versions require NumPy 1 while this app pins NumPy 2.
4. For the common frontend, set MAP_API_TARGET to the deployed MAP app URL and add MAP as an app resource with Can use permission for the frontend app's service principal. The frontend server obtains and refreshes Databricks M2M OAuth tokens using the runtime-injected DATABRICKS_HOST, DATABRICKS_CLIENT_ID and DATABRICKS_CLIENT_SECRET; MAP_API_BEARER_TOKEN is an optional server-side override. Do not put credentials in React or browser configuration.
5. Both launchers bind 0.0.0.0 through app.yaml and use DATABRICKS_APP_PORT in Databricks. Verify source and model accessibility, sufficient compute for BGE/UMAP, persistent run storage and the /map/dataset contract in that environment.
6. A fresh deployment has no completed run: `GET /map/dataset` only reads a saved analysis and returns 503 until one exists. After checking source readiness and approving the model calls, explicitly start a small historical run with `POST /api/v1/map/runs` and `{"limit": 5}`. Poll `GET /api/v1/map/runs/{run_id}` until it is `completed`; if it fails, inspect that run's `worker.log`, `01_filter_report.json` and status before retrying. Do not use `limit: 0` for initial validation because it selects every eligible record.
7. Run the backend tests and frontend browser checks again in the deployment environment. Local worker spawning/file locks are suitable for the current single-instance prototype; durable external job execution and shared coordination need to be configured before horizontally scaling it.

The browser console reports API status, sanitized route and `X-Request-ID`; match that ID with the backend `http_request_complete` log. Run-start, SQL table export, filter counts and worker-stage/error details are written both to Databricks app stdout and `CAPA_DATA_DIR/map-runs/<run_id>/worker.log`. Structured diagnostic fields omit record text, requested IDs, credentials and model prompts; worker exceptions include tracebacks for debugging.

Local execution is verified separately; a Databricks deployment has not been performed. This is a deployment starting point, not a claim of cloud validation.

The source CSV and model bundle belong to the Git repository through LFS, but must be downloaded and placed in approved data/artifact storage when preparing a Databricks deployment. Exclude the entire data directory from app-source upload. These files are not part of the Python wheel, and Git LFS does not bypass app-source size limits. The local forty-record analysis remains local, so a fresh deployment needs a new completed analysis before the dashboard can show results. `CAPA_DATA_DIR=./data` is suitable only for a temporary single deployment; use durable storage if runs must survive redeployments.

References: [Databricks app deployment](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/deploy), [dependency configuration](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/dependencies), [runtime environment and ports](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/system-env), [app development and source limits](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/app-development).

MAP record annotations are persisted with the run artifacts in CAPA_DATA_DIR/map-runs/<run_id>/record_annotations.json. Provision durable run storage and back it up, including annotation history. Per-record revision checks reject stale updates; these annotations do not approve cluster assignments or write to TrackWise. Validate GET dataset/annotations and PUT annotation requests through the deployed frontend proxy as part of acceptance.
